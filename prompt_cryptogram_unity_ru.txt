# ПРОМТ-ПАК — мобильная игра «Эрудиция / Криптограмма»

## Цель
Создать единый набор отдельных UI-референсов для мобильной интеллектуальной игры про криптограммы, литературу и эрудицию.

## Устройство / формат
- Samsung Galaxy S25 FE
- Вертикальная ориентация
- Целевой размер: 1080 × 2340 px
- Все экраны должны быть выполнены в одинаковом масштабе и одинаковых пропорциях телефона
- Каждый экран должен экспортироваться отдельным PNG
- Никаких коллажей
- Никаких листов с несколькими экранами
- Нельзя сжимать или растягивать отдельные экраны

## Визуальный стиль
- Уютное образовательное фэнтези
- Дружелюбная сова-маскот
- Книги, перья, бумага, библиотечная атмосфера
- Мягкие пастельные цвета
- Скруглённые карточки и кнопки
- Крупные и хорошо читаемые элементы
- Дружелюбный, слегка детский стиль
- Тёплый солнечный свет
- Растения, книги, мягкая сказочная атмосфера
- Интерфейс должен выглядеть как полноценная современная мобильная игра
- Много воздуха между элементами
- Минимум визуального шума

## Основная концепция игры
Игрок решает криптограммы и повышает показатель «Эрудиция».

В игре используются:
- цитаты;
- литературные отрывки;
- стихи;
- короткие фразы;
- коллекции авторов и книг;
- достижения;
- статистика;
- магазин;
- система энергии.

## Основная игровая механика
В криптограмме каждая буква заменяется номером или другим обозначением.

Игрок должен постепенно восстановить исходный текст.

Одинаковые цифры всегда соответствуют одинаковым буквам.

Часть букв может быть открыта заранее.

Под каждой буквой находится маленький номер шифра.

Игрок выбирает букву с помощью русской экранной клавиатуры.

## Система «Эрудиция»
Главный показатель прогресса игрока называется:

«Эрудиция»

Пример:
Эрудиция 101

Сложность НЕ выбирается игроком вручную.

Игра автоматически подбирает сложность по текущему показателю «Эрудиция».

Чем выше эрудиция:
- длиннее тексты;
- больше слов;
- сложнее слова;
- реже встречаются очевидные сочетания;
- меньше стартовых подсказок;
- больше вариантов структуры текста.

## Перья
Перья — это энергия для ЗАПУСКА уровней.

Пример:
5/5 перьев

При запуске нового уровня расходуется 1 перо.

Перья НЕ являются жизнями внутри уровня.

Если перья закончились:
0/5

Игрок не может начать новый уровень.

Перья восстанавливаются автоматически через определённое время.

Также игрок может:
- получить перо за просмотр рекламы;
- купить перья в магазине.

## Ошибки внутри уровня
Внутри уровня используются СЕРДЕЧКИ.

Они показывают количество допустимых ошибок.

Перья внутри игрового процесса не используются.

### Классика
5 допустимых ошибок.

Показывать:
❤️ ❤️ ❤️ ❤️ ❤️

### Турбо
3 допустимые ошибки.

Показывать:
❤️ ❤️ ❤️

При неправильном выборе буквы одно сердечко теряется.

Если сердечки закончились, уровень считается проигранным.

## Режим «Классика»
Классика — основной режим для длинных текстов.

Контент:
- цитаты;
- стихи;
- литературные отрывки;
- несколько предложений;
- многострочные тексты.

Количество текста увеличивается вместе с эрудицией.

На низкой эрудиции это может быть небольшая цитата.

На высокой эрудиции это может быть несколько предложений или большой фрагмент текста.

В режиме Классика:
- 5 ошибок;
- более длинные тексты;
- более медленное прохождение;
- больше литературного контента.

## Режим «Турбо»
Турбо НЕ является режимом на время.

Никакого обязательного таймера 15–30 секунд нет.

Смысл Турбо:
- более короткие криптограммы;
- более компактные игровые сессии;
- меньше текста, чем в Классике.

Пример:
2–4 слова на ранних этапах.

При росте эрудиции количество слов тоже увеличивается, но медленнее, чем в Классике.

В режиме Турбо:
- 3 ошибки;
- короткие фразы;
- выражения;
- компактные цитаты;
- быстрое прохождение без таймера.

## Реклама
Реклама должна быть добровольной.

### Реклама после победы
После прохождения уровня показать обычные награды.

Дополнительно предложить:

«Посмотреть рекламу и получить бонус»

Например:
- дополнительная эрудиция;
- дополнительная подсказка;
- дополнительный прогресс коллекции.

Игрок обязательно должен иметь возможность нажать:

«Продолжить»

и не смотреть рекламу.

### Реклама для восстановления перьев
Если у игрока 0/5 перьев, показать экран:

«Перья закончились»

Показать:
- таймер восстановления следующего пера;
- кнопку просмотра рекламы;
- награду +1 перо;
- кнопку магазина;
- кнопку возврата в меню.

Пример CTA:

«Посмотреть рекламу»
«+1 перо»

## Общие ограничения для генерации UI
Нельзя:
- делать тёмный хоррор-интерфейс;
- перегружать экран;
- делать очень мелкий текст;
- использовать разные размеры телефонов;
- создавать коллажи;
- объединять несколько экранов в один PNG;
- использовать перья как ошибки внутри уровня;
- использовать сердечки как энергию меню;
- делать Турбо обязательным режимом на время;
- добавлять ручной выбор сложности.

# ТЕХНИЧЕСКАЯ РЕАЛИЗАЦИЯ В UNITY

Проект должен разрабатываться в Unity.

## Основные требования

- Использовать актуальную стабильную LTS-версию Unity.
- Игра должна быть мобильной, с основной ориентацией Portrait.
- Целевой дизайн интерфейса: 1080 × 2340 px.
- Использовать Unity UI через Canvas.
- Canvas Scaler настроить через:
  - UI Scale Mode: Scale With Screen Size
  - Reference Resolution: 1080 × 2340
  - Screen Match Mode: Match Width Or Height
- Интерфейс должен корректно адаптироваться к экранам с близким соотношением сторон.
- Учитывать Safe Area мобильных устройств.

## КРИТИЧЕСКИ ВАЖНО: UI НЕ СОЗДАВАТЬ ДИНАМИЧЕСКИ ЧЕРЕЗ КОД

Все основные элементы интерфейса должны существовать как реальные GameObject-объекты в Unity Scene / Prefab и быть видимы в Hierarchy.

НЕЛЬЗЯ:
- полностью генерировать интерфейс из C#;
- создавать кнопки, тексты, панели, картинки и контейнеры только через Instantiate во время запуска;
- строить всю сцену программно;
- создавать UI через циклы и скрипты без представления элементов в редакторе;
- хранить весь интерфейс только как данные без визуальных объектов сцены.

НУЖНО:
- каждый экран должен быть представлен отдельным GameObject-контейнером;
- все кнопки, тексты, иконки, панели, изображения и декоративные элементы должны быть размещены в сцене заранее;
- элементы должны быть доступны для выбора, перемещения и редактирования вручную через Unity Editor;
- настройки элементов должны быть доступны через Inspector;
- для повторяющихся компонентов можно использовать Prefab;
- Prefab должен оставаться визуально редактируемым в Unity Editor;
- ссылки на UI должны задаваться через SerializeField / Inspector, а не находиться каждый раз через GameObject.Find;
- бизнес-логика может быть написана на C#, но визуальная структура должна оставаться в Scene / Prefab.

Главная цель этого требования:
после генерации проекта разработчик должен иметь возможность открыть Unity, выбрать любой элемент интерфейса мышкой в Hierarchy и вручную изменить:
- позицию;
- размер;
- цвет;
- спрайт;
- текст;
- отступы;
- шрифт;
- анимацию;
- активность объекта;
- связи с другими элементами.

Это необходимо для дальнейшего дебага и ручной доработки.

## РЕКОМЕНДУЕМАЯ СТРУКТУРА HIERARCHY

Пример:

MainScene
└── Canvas
    ├── SafeArea
    │   ├── Screen_MainMenu
    │   ├── Screen_ModeSelection
    │   ├── Screen_GameplayClassic
    │   ├── Screen_GameplayTurbo
    │   ├── Screen_Victory
    │   ├── Screen_NoFeathers
    │   ├── Screen_Statistics
    │   ├── Screen_Collections
    │   ├── Screen_AuthorDetails
    │   ├── Screen_Achievements
    │   ├── Screen_Shop
    │   └── Screen_Settings
    └── GlobalPopupLayer

Каждый Screen_* должен быть отдельным объектом-контейнером.

При переключении экранов допустимо просто менять SetActive(true/false).

Не требуется загружать отдельную сцену для каждой вкладки.

## GAMEPLAY SCREEN

Экран игрового процесса тоже не должен собираться полностью через код.

В Scene / Prefab должны заранее существовать:

Screen_GameplayClassic
├── Background
├── TopBar
│   ├── Button_BackOrPause
│   ├── Label_Mode
│   ├── EruditionBadge
│   ├── HeartsContainer
│   │   ├── Heart_01
│   │   ├── Heart_02
│   │   ├── Heart_03
│   │   ├── Heart_04
│   │   └── Heart_05
│   └── Button_Hint
├── PuzzlePanel
│   └── PuzzleContent
└── Keyboard
    ├── Row_01
    ├── Row_02
    └── Row_03

Для Турбо:
- отдельный Screen_GameplayTurbo;
- 3 заранее размещённых сердца.

Допускается программно менять:
- текст букв;
- номера;
- состояние открыто/закрыто;
- цвет;
- состояние клавиш;
- количество активных строк.

Но сами основные контейнеры и UI-компоненты должны существовать заранее.

## КРИПТОГРАММА И ЯЧЕЙКИ БУКВ

Для букв можно использовать Prefab LetterCell.

LetterCell должен содержать:
- Text/Label буквы;
- линию/подчёркивание;
- Text с номером шифра;
- фон при необходимости;
- состояния Selected / Correct / Error.

Prefab должен быть создан в Unity Editor и доступен для ручного редактирования.

Допускается создавать LetterCell из Prefab во время игры в зависимости от длины текста.

Но:
- сам Prefab должен существовать как визуальный объект;
- PuzzlePanel и все Layout-контейнеры должны находиться в сцене;
- код не должен вручную создавать Text, Image, Button и LayoutGroup с нуля.

## КЛАВИАТУРА

Русская клавиатура должна быть создана визуально в Unity Editor.

Каждая кнопка буквы должна существовать в Hierarchy или быть частью заранее созданного Keyboard Prefab.

Не генерировать всю клавиатуру программно.

Например:

Keyboard
├── Row_01
│   ├── Key_Й
│   ├── Key_Ц
│   ├── Key_У
│   └── ...
├── Row_02
└── Row_03

Это позволит вручную менять размеры клавиш и отступы.

## PREFABS

Создать Prefab для часто повторяющихся элементов:

- BottomNavigation
- TopBar
- FeatherEnergyWidget
- EruditionBadge
- HeartIndicator
- HintButton
- LetterCell
- AuthorCard
- CollectionCard
- AchievementCard
- ShopItemCard
- RewardCard
- OwlMascotBlock

Все Prefab должны быть полностью визуально редактируемыми.

## ТЕКСТ

Предпочтительно использовать TextMeshPro.

Все тексты должны:
- быть доступны в Inspector;
- иметь корректные русские символы;
- использовать единый набор шрифтов;
- автоматически масштабироваться только там, где это действительно нужно.

Не использовать системный шрифт как обязательную финальную зависимость.

## SPRITES И ГРАФИКА

Все декоративные элементы должны быть отдельными Sprite/Image-компонентами, когда это имеет смысл.

Например:
- сова;
- книги;
- перо;
- корона;
- сердечки;
- лампочка;
- фон;
- карточки;
- тематические иллюстрации.

Не запекать весь экран в одну картинку.

ВАЖНО:
референсы являются ориентиром по стилю, а не готовым фоном интерфейса.

UI должен быть собран из отдельных элементов, чтобы его можно было редактировать.

## АНИМАЦИИ

Если добавляются анимации:
- использовать Animator / Animation Clips или Tween-систему;
- анимируемые объекты должны существовать в сцене;
- не создавать визуальные элементы только ради анимации через код.

Примеры:
- лёгкое покачивание совы;
- появление карточек;
- анимация потери сердца;
- появление правильной буквы;
- мягкая анимация награды;
- анимация восстановления пера.

## СКРИПТЫ

Код использовать только для логики.

Примеры:
- GameManager;
- UIManager;
- ScreenManager;
- EnergyManager;
- PuzzleManager;
- EruditionManager;
- SaveManager;
- AdsManager;
- AudioManager.

Скрипты должны получать ссылки на UI через Inspector.

Пример подхода:

[SerializeField] private GameObject screenMainMenu;
[SerializeField] private TMP_Text eruditionText;
[SerializeField] private Button classicButton;

Не использовать GameObject.Find для основной архитектуры.

Не создавать UI-иерархию из кода.

## SCREEN MANAGER

ScreenManager должен переключать заранее существующие Screen GameObject.

Пример логики:

ShowMainMenu()
ShowModeSelection()
ShowClassicGame()
ShowTurboGame()
ShowStatistics()
ShowCollections()
ShowAchievements()
ShowShop()
ShowSettings()

Экран должен включаться через SetActive(true), предыдущий выключаться.

## DEBUG

Добавить возможность удобно тестировать игру в Unity Editor.

Создать отдельный DebugPanel, который можно включать в Editor/Development Build.

DebugPanel должен позволять:
- изменить Эрудицию;
- добавить/убрать перья;
- выставить 0/5 перьев;
- восстановить все перья;
- изменить количество подсказок;
- открыть любой экран;
- принудительно вызвать победу;
- принудительно вызвать поражение;
- выставить количество ошибок;
- открыть тестовую криптограмму;
- сбросить прогресс;
- открыть все коллекции;
- разблокировать достижения.

DebugPanel должен быть обычным UI-объектом в Scene, а не скрытой системой без интерфейса.

## СОХРАНЕНИЯ

Для первой версии можно использовать PlayerPrefs или простой JSON-save.

Сохранять:
- Эрудицию;
- перья;
- время восстановления перьев;
- подсказки;
- открытые коллекции;
- достижения;
- статистику;
- настройки;
- прогресс игрока.

Архитектуру сделать так, чтобы позже можно было заменить систему сохранений.

## РЕКЛАМА

AdsManager должен иметь отдельный абстрактный слой.

Для тестирования в Unity Editor вместо реальной рекламы должна быть возможность вызвать Fake Rewarded Ad.

В Editor:
- нажатие «Посмотреть рекламу» может сразу вызывать успешный callback;
- после этого начисляется бонус.

Для production позже подключить рекламный SDK.

Реклама используется:
1. после победы — дополнительная награда;
2. при 0 перьев — восстановление +1 пера.

## ИТОГОВОЕ ТРЕБОВАНИЕ К CODEX / РАЗРАБОТЧИКУ

Не создавать проект как набор экранов, полностью построенных C#-кодом.

После завершения работы я должен иметь возможность:

1. Открыть проект Unity.
2. Открыть основную сцену.
3. Увидеть все экраны в Hierarchy.
4. Раскрыть любой экран.
5. Выбрать любую кнопку или текст.
6. Изменить его через Inspector.
7. Сразу увидеть изменения в Scene/Game View.
8. Запустить Play Mode и протестировать логику.

Если какой-либо крупный элемент интерфейса невозможно визуально найти и отредактировать в Unity Editor без изменения C#-кода, реализация считается неправильной.
